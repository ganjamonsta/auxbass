# 🛠️ Искусство разработки: Ветки, Фиксы и Релизы

Разработка — это не просто написание кода, а процесс его безопасной доставки до пользователя. Вот как это делают профессионалы.

---

## 🌿 Стратегия веток (Git Flow упрощенно)

Вместо того чтобы всё валить в одну кучу, мы разделяем код по "слоям":

| Ветка | Роль | Статус |
| --- | --- | --- |
| `main` | **Production**. То, что сейчас видят пользователи. Только стабильный код. | 🟢 Стабильно |
| `dev` | **Staging**. Место для тестирования всех новых фишек перед релизом. | 🟡 Тестируется |
| `feature/...` | **Фичи**. Временная ветка для одной конкретной задачи. | 🔴 В работе |
| `fix/...` | **Баг-фиксы**. Временная ветка для исправления ошибки. | 🔴 В работе |

---

## 🔄 Жизненный цикл задачи (Feature)

Допустим, ты хочешь добавить "Таймер сна".

1. **Создание ветки**:
   Находясь в `dev`, создаешь ветку `feature/sleep-timer`.
2. **Разработка локально**:
   Пишешь код, тестируешь через `run_dev.bat`.
3. **Пуш в облако**:
   `git push origin feature/sleep-timer`.
4. **Проверка на сервере (Staging)**:
   Вливаешь свою фичу в `dev` на GitHub, подтягиваешь на сервере в папку `/opt/tg_player_test`. Проверяешь на тест-боте.
5. **Релиз**:
   Если всё ок, вливаешь `dev` в `main` и обновляешь Прод.

## 🐞 Как фиксить баги

Баги бывают двух типов:

### 1. "Нужно поправить когда-нибудь" (Обычный баг)
- Создаешь ветку от `dev`: `fix/wrong-artist-name`.
- Спокойно правишь, тестируешь в Тест-боте.
- Вливаешь в `dev` к следующему "большому" обновлению.

### 2. "ВСЁ СЛОМАЛОСЬ ПРЯМО СЕЙЧАС!" (Hotfix)
- Создаешь ветку **напрямую от `main`**: `hotfix/crash-on-start`.
- Быстро фиксишь баг.
- Вливаешь **сразу в `main`** и деплоишь на Прод.
- Не забудь потом влить этот фикс и в `dev` тоже.

## 🧐 Полезные советы для порядка

### 1. Один коммит = одна мысль
Не делай огромных коммитов на 50 файлов. Лучше 10 маленьких.
- *Плохо:* `git commit -m "обновил всё"`
- *Хорошо:* `git commit -m "исправил цвет кнопки в плеере"`

### 2. Используй GitHub Issues
Записывай туда все идеи и баги. Не держи их в голове. Когда начинаешь делать задачу — привязывай её к ветке.

### 3. Версионирование
Когда заливаешь большой патч, ставь "тег" (метку версии):
`git tag -a v1.1.0 -m "Big UI update"`
Это позволит тебе в любой момент откатиться к конкретной версии плеера, если что-то пойдет не так через неделю.

## 📈 Твой путь роста
1. **Solo-dev**: Всё в `main` (как у тебя было).
2. **Junior**: Есть `main` и `dev`, боишься сломать прод.
3. **Middle**: Работаешь через `feature`-ветки, делаешь маленькие коммиты.
4. **Senior**: Пишешь тесты (pytest) перед тем, как отправить код в `dev`. (Это твой следующий шаг!)
